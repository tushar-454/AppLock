# Native protection architecture

This is a personal Android utility, using Expo 58 / React Native 0.88 and the existing NativeWind 5 / Tailwind 4 setup. Android 11 (API 30) is the minimum because AndroidX Biometric supports the combined strong-biometric and device-credential authenticator configuration from that API. The release targets API 36 and compiles against API 37, following the installed SDK's version catalog.

## Components and ownership

`modules/app-lock/android` is a local Expo module discovered automatically by Expo Autolinking. Its library manifest merges its service, activity, receivers, permissions, and intent visibility queries into the application. `plugins/with-app-lock.js` reproducibly sets the minimum API, disables unused image decoders, provides optional personal signing, and removes network permissions from release builds. `android/` is generated and ignored; never maintain native code there. A fresh prebuild reproduces the integration.

`AppLockModule` exposes typed asynchronous discovery, configuration, status and settings methods. Its accessibility-settings observer and in-process events refresh the UI. React Native AppState is used only to refresh UI status after returning from Settings. It has no role in enforcement. React Native does not need to be mounted or running for protection. UI event subscriptions and permission observers detach when the UI backgrounds; native protection events do not drive JavaScript refreshes in the background. A previously opened RN runtime may remain in process memory under the normal React Native lifecycle, but enforcement does not run JavaScript tasks.

`AppCatalog` queries MAIN/LAUNCHER activities, resolves real labels and icons, deduplicates packages, sorts with the user's locale, and caches metadata. Icons are bounded 96-pixel PNGs in private cache storage. Package broadcasts invalidate the cache. Only visible launchable apps in this Android user/profile are listed. Targeted `<queries>` for launchers, home, keyboards and dialers avoid `QUERY_ALL_PACKAGES`; hidden packages, private spaces and other users are outside scope. No package inventory leaves the device.

`ProtectionStore` owns the authoritative package set in device-protected SharedPreferences. A process-wide lock serializes read-modify-write across instances; `commit()` atomically persists before bridge success. There are no stored grants, biometric templates, PINs, encryption keys or passwords. Invalid package identifiers are rejected. Malformed preferences are detected and surfaced as damaged configuration; unreadable package records cannot be reconstructed. Android's preference-file backup can recover an interrupted write, but it cannot restore cleared app data. App backup is disabled. Uninstall broadcasts remove stale records while package upgrades retain them.

`AppLockService` is an Android-bound, Direct Boot-aware AccessibilityService. It subscribes only to TYPE_WINDOW_STATE_CHANGED with zero batching delay. Only `packageName`, `className` and `eventType` are read. `canRetrieveWindowContent=false`; no event text, source nodes, root windows, gestures, screenshots, UsageStats or polling are used. TYPE_WINDOWS_CHANGED alone does not reliably identify the package without broader window retrieval; it is deliberately not requested. A single delayed task expires an authenticated session; no periodic work runs.

`LockEngine` is pure Kotlin and accepts a monotonic clock. It owns a single foreground session, package-bound random request ID and explicit states. Duplicate events cannot open duplicate prompts. Leaving for an unrelated launchable app (including AppLock's configuration screen) invalidates the session. Known keyboard, permission-controller and SystemUI metadata is ignored, preserving sessions through temporary system interactions. Launchers invalidate sessions, including overview events where the launcher supplies them. Grants expire after five minutes. If a transient system window is active, enforcement resumes at the next ordinary app event. Screen off, service disconnection, boot and process recreation clear trust. Nothing restores an authenticated state from disk. Unsupported non-launchable foreground components and OEM event differences remain a detection limitation.

`LockSurface` creates an opaque full-screen native surface with a real app icon/label, Android authentication button and safe Home action. The service attaches it using TYPE_ACCESSIBILITY_OVERLAY. It is touchable, focusable and FLAG_SECURE; no transparent or non-touchable cover exposes the underlying interactive content. System navigation remains available. Emergency calls, launchers, Settings, dialers, keyboards, AppLock itself and recovery components cannot be selected for protection.

`AuthenticationActivity` is a non-exported, opaque, FLAG_SECURE FragmentActivity in its own task, excluded from recents. The cover is attached before requesting the activity. Once the activity resumes, its opaque window replaces the overlay so the overlay cannot occlude Android's prompt or credential UI. If the platform suppresses the activity start, the cover remains with an explicit Unlock action. The service does not retry automatically in a loop. Cancellation requests Android's Home global action while retaining a cover until a new foreground event; it never grants access.

The official AndroidX `BiometricPrompt` uses BIOMETRIC_STRONG | DEVICE_CREDENTIAL. Availability is checked for both combined and credential-only authenticators. Credential-only authentication remains available without biometric hardware/enrollment and is retried after biometric lockout when supported. Only `onAuthenticationSucceeded` for the still-current ID in AUTHENTICATING state can create a grant. Failed attempts leave Android's prompt pending; errors and cancellation do not grant access. Rotation reattaches AndroidX callbacks without launching a second prompt. Activity destruction never authenticates. Old callbacks and rapid switches cannot grant a different app's session. The prompt never asks for a PIN in an AppLock form.

## Boot and service recovery

The boot receiver recognizes LOCKED_BOOT_COMPLETED, BOOT_COMPLETED, USER_UNLOCKED and MY_PACKAGE_REPLACED. It accesses only the device-protected package set and clears any in-memory session. The accessibility service is Direct Boot-aware; Android controls binding and recovery of the user-enabled service. Neither the receiver nor JS calls startService/startForegroundService, attempts to enable accessibility, requests battery exemptions, or loops to restart a killed service. Before first unlock the engine defers to the system keyguard; no third-party prompt is shown over it. The catalog waits for credential unlock. Fingerprints can be unavailable after reboot until the device credential has been entered. Initial service binding and first usable post-unlock app events are Android-controlled and require physical-device verification. Force-stop and permission revocation disable protection until Android/user restores the service.

## Security boundary and limitations

This is an interaction barrier for ordinary foreground apps, not an OS security boundary, parental-control agent, device-owner policy or replacement for screen lock. Android emits accessibility events after windows change; zero-frame exposure cannot be guaranteed. System bars, notifications, picture-in-picture, split-screen, secondary displays, work profiles and recent-task previews are not reliably covered. FLAG_SECURE secures AppLock's own windows only; it cannot erase another app's task thumbnails. Users can disable, uninstall, clear data or change AppLock's settings without authenticating; this is intentional recovery access. Do not claim tamper resistance. Missing/corrupt configuration and a disconnected service are visible in the UI.
